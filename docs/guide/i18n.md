# Translations

Every refusal nexus writes starts out in English: `The title field must be at least 3 characters.` That is fine for a developer reading a `422`, but if your blog has German readers, the sign up form should tell them what is wrong in German.

`nexus::Messages` does that. It holds one catalog per language, picks the best one for each request from its `Accept-Language` header, and renders every field message of a refused input in that language before the response goes out. Your actions don't change at all. The same catalogs are there for your own text too, such as a mail's subject.

## Adding a catalog

A catalog is a JSON object of keys to messages. The blog keeps its German one in `resources/lang/de.json`:

```json title="resources/lang/de.json"
{
  "rule": {
    "required": "Das Feld {label} ist erforderlich.",
    "min": {
      "string": "Das Feld {label} muss mindestens {min} Zeichen lang sein.",
      "integer": "Das Feld {label} muss mindestens {min} sein.",
      "list": "Das Feld {label} muss mindestens {min} Einträge haben."
    },
    "email": "Das Feld {label} muss eine gültige E-Mail-Adresse sein.",
    "unique": "Diese {label} ist bereits vergeben."
  },
  "label": {
    "title": "Titel",
    "password": "Passwort",
    "Blog::Inputs::Registration": {
      "email": "E-Mail-Adresse"
    }
  },
  "mail": {
    "welcome": {
      "subject": "Willkommen bei {blog}"
    }
  }
}
```

Nested objects are joined with dots, so `"rule": { "min": { "string": ... } }` is the key `rule.min.string`. You may nest as deep as reads well, or write the dotted keys flat; both end up the same.

The kernel binds one `nexus::Messages` for the whole app. You add your catalogs to it in your extension's `boot()`, which runs once the kernel is ready and before the first request:

```echo title="src/App.eco"
/**
 * Input messages and the welcome subject in German, next to the English ones.
 */
public function boot(nexus::Kernel $kernel) : status<nexus::BootError>
{
    $german = guard json::parse(std::embed::text('../resources/lang/de.json')) else ($e) {
        return .error(.extension('blog', "resources/lang/de.json: {$e->message()}"));
    };
    $kernel->services->get<nexus::Messages>()->add('de', $german);
    return .ok;
}
```

`std::embed::text` reads the file at compile time, relative to the source file, so the catalog is part of the binary and there is nothing to deploy next to it. If the catalog is not valid JSON, this `boot()` stops the app with the file's name, rather than letting it run half untranslated.

You may add as many locales as you like, and add to the same locale more than once; a key given twice keeps the last. For a single message, `put('de', 'mail.welcome.subject', '...')` does the same without a file.

## How the language is picked

For a request, `Messages` reads the `Accept-Language` header and tries each language range in order of quality. A regional tag like `de-CH` is taken as it is when you have a `de-CH` catalog, and as `de` otherwise. When nothing fits, the answer is `en`. Only locales you have added a catalog for are ever picked, so a client asking for French gets English, not an empty message.

You may ask which locale a request speaks with `$payload->locale()`. The blog's `Register` action does, and carries the answer along with the signal it sends, so the welcome mail goes out in the language the user signed up in:

```echo title="src/Actions/Users/Register.eco"
try $this->signals->send(UserRegistered($user: $made->id, $locale: $payload->locale()));
```

Carrying the locale along like that matters. A [task](./tasks.md) runs later, on a worker, without the request, so it cannot read the header itself.

Commands and tasks have no `Accept-Language` at all. For them the locale comes from the `LANG` environment variable instead, with `de_CH.UTF-8` read as `de-CH`. So `LANG=de_DE.UTF-8 echoc run -- posts:create ...` prints its refusals in German.

## Translating input messages

When an input is refused, every field error carries a stable `code` (`required`, `min`, `email`, ...), the input type and field it belongs to, the kind of value the field holds (`string`, `integer`, `list`, ...) and the rule's parameters. `Messages` uses them to look for the best message, trying each locale of the chain in turn. For a `de-CH` request that is `de-ch`, then `de`, then `en`.

Within each locale, a refusal of the field `title` of `Blog::Inputs::NewPost` with code `min` looks for:

1. `Blog::Inputs::NewPost.title.min`, a message for this one field,
2. `rule.min.string`, the rule's message for this kind of value,
3. `rule.min`, the rule's message for any value.

The first one found wins. If no locale of the chain has any of them, the English message stays as it was.

Why the kind? Because "at least 3" reads differently for text, numbers and lists. In German, "mindestens 3 Zeichen" is not "mindestens 3 Einträge", and the kind lets one catalog say both.

::: tip
The chain goes locale by locale, and within a locale from the most specific key to the least. A German `rule.unique` therefore wins over an English message written for one field. Translate a field's own message under the field's key in each language you support.
:::

### Labels and holes

A message has holes in braces, filled when it is rendered. `{label}` is how the message calls the field, and is looked up the same way: `label.Blog::Inputs::Registration.email`, then `label.email`, then the English label. That is why the catalog above can call the sign up form's `email` field "E-Mail-Adresse" without touching any other input's `email`.

The other holes are the rule's parameters, named as the rule names them: `{min}`, `{max}`, `{size}`, `{values}`, `{value}`, `{other}` and `{date}`.

The response that carries translated messages also gets a `Content-Language` header with the locale used, so a client knows what it is showing.

## English defaults

The English messages come from nexus itself, and you may override them per field, right on the input. `#[nexus::label]` says how messages call a field, and `#[nexus::message]` replaces the English message for one code:

```echo title="src/Inputs/Registration.eco"
#[nexus::input]
public struct Registration
{
    #[nexus::rule: { trim: true, lower: true, email: true, max: 190, check: 'Blog::Rules::UniqueEmail' }]
    #[nexus::label: 'e-mail address']
    #[nexus::message: { unique: 'Someone already signed up with that e-mail address.' }]
    public string $email;

    // ...
}
```

Without a label, the field's name is made readable. `nexus gen` writes each `#[nexus::message]` into the English catalog, so it takes part in the same lookup as everything else: the `en` key `Blog::Inputs::Registration.email.unique` is now that sentence.

A rule class of your own gives its English message when it fails, with the same holes:

```echo title="src/Rules/UniqueEmail.eco"
if ($found != null) {
    $v->fail('unique', 'The {label} has already been taken.');
}
```

Its code is what catalogs key on, so `rule.unique` in `de.json` translates it. [Input and validation](./input.md) covers rules and their codes in full.

## Translating your own text

A catalog may hold any key, not only input messages, and you are free to read from it wherever you render text for people. `get(locale, key)` gives the message under a key in exactly that locale, or null. `chain(locale)` gives the locales to try, in order, so a lookup with fallback is a short loop:

```echo title="src/Mail/WelcomeMail.eco"
public const function subject() : string
{
    // de-CH, then de, then en
    foreach ($this->messages->chain($this->locale) as const &$locale) {
        $translated = guard $this->messages->get($locale, 'mail.welcome.subject') else {
            continue;
        };
        return str::replace($translated, '{blog}', $this->blog);
    }
    return "Welcome to {$this->blog}";
}
```

The English text sits in the code as the last resort, so the subject is never empty even without a catalog. The [mail](./mail.md) guide shows how this mail is composed and sent from a task.

### Problems you render yourself

The kernel translates field messages on the way out for every request, and a generated command does the same for what it prints. If you ever turn a `nexus::Problem` into text yourself, `$payload->localized($p)` gives you the problem with its field messages in the payload's language.
